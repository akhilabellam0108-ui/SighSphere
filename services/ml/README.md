# ML training

Training runs in **Google Colab**, not on your laptop. Two reasons:

1. Free GPU.
2. Local Python here is **3.14**, which is ahead of PyTorch/MediaPipe wheel support. Colab
   runs 3.11.

You need no local Python for the MVP — all vision runs in the browser (see
[../../docs/architecture.md](../../docs/architecture.md)). The only local Python you might
want is `numpy`, to run the parity check.

---

## Files

| File | Purpose |
| --- | --- |
| `features.py` | **Python mirror of `apps/web/src/lib/features.ts`.** Must match exactly. |
| `check_parity.py` | Proves it matches. Run after every change to either file. |
| `dataset.py` | JSONL loading, **signer-held-out** splits, augmentation. |
| `train.py` | Model ladder (linear → cnn → gru), eval, ONNX export. |
| `fixtures/parity.json` | Generated by the TS test suite. Do not edit by hand. |
| `build_isl_pack.py` | Builds the app's **built-in ISL sign packs** from the INCLUDE dataset (see below). |

## The parity check — run this before you trust any number

`features.py` and `features.ts` must produce identical vectors. If they drift, your Colab
accuracy describes a model that does not exist in the app, and nothing downstream will tell
you. It is the highest-value 10 seconds in this repo:

```bash
npm test --workspace @signsphere/web     # regenerates fixtures/parity.json from the TS code
cd services/ml && python check_parity.py # asserts Python agrees
```

Currently passes with a max difference of exactly 0. Two gotchas it guards:

- JS `Math.round` rounds `.5` **up**; Python's `round()` rounds `.5` **to even**.
  `resample_window` uses `floor(x + 0.5)`.
- Float32 truncation — both sides cast to float32 at the end.

## Workflow

**1. Collect.** In the app's **Record** screen, capture samples, then *Export JSONL*.
Read [../../docs/data-collection-protocol.md](../../docs/data-collection-protocol.md) before
recording anyone else. Export skips anything without training consent and says how many it
skipped.

**2. Train in Colab.**

```python
!git clone <your-repo> signsphere
%cd signsphere/services/ml
!pip install -q numpy torch onnx
# upload samples.jsonl via the Files pane

!python train.py --data samples.jsonl --model linear --epochs 40   # Rung 0 BASELINE FIRST
!python train.py --data samples.jsonl --model cnn    --epochs 60   # Rung 1
```

Always run `--model linear` first and write the number down. If `cnn` cannot beat a linear
model on flattened landmarks, the problem is your data (mislabels, one signer, leakage), not
your architecture. Chasing architectures past a broken dataset is the classic way to waste
a month.

**3. Ship the model.**

```bash
# train.py writes to ../../models/
models/sign-cnn-v1.onnx           # copy to apps/web/public/models/
models/sign-cnn-v1.labels.json    # class order — the app needs this
models/sign-cnn-v1.metrics.json   # commit this; it is your evidence
```

Then set `VITE_MODEL_URL=/models/sign-cnn-v1.onnx` and implement `OnnxClassifier` in
`apps/web/src/lib/classifier.ts` (the Week 8 checklist is in that file). It deliberately
throws today rather than returning fake predictions — a stub that silently returns nonsense
is indistinguishable from a working model in a demo.

## Rules that are not negotiable

**Split by signer, never randomly.** `dataset.py` has no `random_split` function on purpose.
A random split puts the same person's takes in train and test; the model memorises their hand
size, speed, and sleeve and scores 30–40 points higher than reality. Every implausible
sign-recognition result you will read made this mistake.

**Report the held-out-signer number.** Not validation, not training. If it is 76%, the report
says 76%.

**Augment train only.** Never val or test.

**Watch for these before believing a good result:**

| Symptom | Likely cause |
| --- | --- |
| Test ≫ val accuracy | Signer leakage — check the split |
| One class at 0% | Mislabelled recordings, or fewer than ~5 examples |
| High accuracy, useless in browser | Feature parity broken — run `check_parity.py` |
| Great on you, bad on everyone | Too few signers; no fix but more people |
| Accuracy drops after adding data | New data is mislabelled — QC that session |

## Ship gate (PLAN.md §5.3)

- **≥90% top-1, leave-signers-out, on 100 signs**
- **≤300 ms p95 client-side on a mid-range Android** (measure on the real device)
- An explicit "unclear / not a sign" rejection class

Miss it? Cut the vocabulary (100 → 60), don't ship a model that guesses confidently.

## Built-in ISL signs from INCLUDE (so the app recognises signs out of the box)

[INCLUDE](https://zenodo.org/records/4010759) (AI4Bharat, ACM MM 2020) is a CC BY 4.0 dataset
of 263 isolated ISL signs, 4,292 videos. `build_isl_pack.py` turns the videos for chosen signs
into a small JSON "sign pack" of feature windows — computed with the same MediaPipe models and
the same `features.py` the browser uses — which users install from **Record signs → Built-in
ISL signs**. Installed examples live in the browser's IndexedDB, so they work offline.

| Pack | Signs | Download from Zenodo |
| --- | --- | --- |
| `sos` → `isl-include-sos.json` | HOSPITAL, DOCTOR, POLICE, MEDICINE, SICK, DEAF | only the parts containing them |
| `everyday` → `isl-include-everyday.json` | the SOS signs + 22 everyday signs | more parts (~15–25 GB transient) |

In Colab:

```python
!pip install -q -r requirements-pack.txt
!python build_isl_pack.py --preset sos --download --work /content/include
# writes ../../apps/web/public/datasets/isl-include-sos.json
```

Then commit `apps/web/public/datasets/*.json` and redeploy; the Install button appears
automatically. Zips are deleted as soon as the needed folders are extracted.

Not in INCLUDE, so they must be **recorded with a fluent signer**: HELP, PAIN, FIRE,
AMBULANCE, EMERGENCY. Keep the attribution that the pack carries; it is shown in the app.
Accuracy on new signers is not INCLUDE's paper accuracy — measure it and report what you get.
